- 本文合并原设备发现逻辑与后续模块讨论，同一功能集中维护，不再另建重复设计文档。
- 产品需求描述完整产品，阶段计划描述交付顺序，本文描述设备发现这一功能。“第一个功能”不改变阶段计划中的实施节点编号。

## 1. 当前功能与边界

当前闭环：

1. 程序启动时发现已经接入的相关设备。
2. 运行期间监听设备接入、移除和变化。
3. 获取设备信息，按可修改的关注规则匹配，识别系统已经呈现的功能与访问入口。
4. 保存连接事件历史，保存成功后提供供程序使用的结果。

当前同时处理多个接入设备。结果面向程序，具体对外读取方式、展示页面和历史查询接口暂不实现。

### 1.1 接入范围

- 树莓派 USB → CH340 转接器 → 开发板 UART。
- 树莓派 USB → 开发板 USB OTG；可能呈现虚拟串口、USB 网络、复合功能或 Rockchip 烧录模式。
- 用户通过关注规则决定哪些设备类型进入正常结果和连接历史。

CH340 是转接芯片类型；USB OTG 描述接口能力和角色，具体功能取决于板端系统与模式。规则匹配产品类型，实际功能还需要结合接口、驱动和资源信息判断。USB 身份被发现不等于通道已经就绪。

### 1.2 本轮边界

- 只读取系统元数据，不主动打开串口、调整波特率、发送探测命令或尝试 SSH 登录。
- 不执行模式切换、烧录、文件传输或硬件控制。
- 不记录波特率、校验位等通信配置。
- 未匹配关注规则的设备不进入正常设备结果和连接历史。采集模块仍可向编排层提供原始信息，由编排层筛选。
- 未知设备人工适配、板卡绑定、跨位置识别同一实物、复用板卡配置保留在完整产品需求中，当前不展开。
- 暂不引入插件运行框架、通用事件总线或覆盖所有业务的历史系统。

## 2. 系统已有能力

### 2.1 Linux 与应用的分工

以 CH340 为例：

```text
USB 接入产生电气状态变化
    ↓
USB 硬件与 Linux 发现设备，读取 USB 描述信息
    ↓
根据设备及接口信息匹配驱动，需要时加载本机已有模块
    ↓
驱动管理设备，注册串口等系统资源
    ↓
系统提供 /dev/ttyUSB… 等入口，并产生设备事件
```

Linux 的 `ch341` 驱动支持相应 CH340 设备，一个驱动可以管理多个设备。应用复用操作系统的枚举、驱动和通知能力。

| 能力 | 可复用实现 | 用途 |
|---|---|---|
| USB 枚举与驱动管理 | Linux USB 子系统及已有驱动 | 获取系统已经识别的设备和接口 |
| 枚举、变化通知 | udev/libudev；Python 可使用 pyudev | 扫描设备、接收事件 |
| 父子设备关系 | sysfs、libudev/pyudev | 将串口和网络接口关联到 USB 父设备 |
| 串口信息查询 | pySerial 等 | 按实际需要复用枚举能力 |
| 文件、结构化数据、锁 | 标准库及成熟库 | 规则读写与历史追加 |

当前方向为 Python 集成，优先复用已有能力；具体依赖、版本和封装方式在实现时选择。

### 2.2 事件含义

- 运行期间可收到针对具体设备的新增、移除、变化等通知，以及当时可获得的属性。
- 通知是增量事件，不直接返回完整设备列表，也不保证提供完整属性差异。
- 程序启动前已经接入的设备需要单独枚举。
- 一个复合 USB 设备可能产生 USB、串口、网络等多个层级的通知，一次物理插入可能有多次事件。
- 移除后设备文件或属性可能已消失，处理时保留事件中的可用信息，必要时结合此前观察到的连接信息。

## 3. 信息与记录的含义

扫描与通知采用一致的设备信息描述。以下为逻辑字段，具体类、字段名称和类型尚未确定。

| 信息 | 含义 |
|---|---|
| 观察时间 | 本程序发现或接收到事件的时间 |
| 来源与动作 | 启动扫描、主动扫描，或系统报告的新增、变化、移除 |
| USB 连接位置、系统设备路径 | 跟踪该位置的连接情况，包含必要的集线器层级 |
| VID/PID | 产品类型匹配依据 |
| 名称、序列号等可选属性 | 系统实际提供时保留，允许缺失 |
| USB 父设备、接口、驱动 | 关联资源、说明识别依据 |
| 功能、访问入口及可用情况 | 例如串口节点、网络接口 |
| 匹配得到的 Key | 编排层调用规则模块后加入记录 |

名称、序列号等可选字段缺失不阻止记录；无法取得匹配所需的 VID/PID 时不凭空识别。串口、网络资源尚未生成时，不宣称通道可用。移除事件可结合先前观察到的信息记录。

位置与身份的边界：

- 历史主要按 USB 连接位置组织，记录这个位置何时观察到接入、变化或移除。
- `/dev/ttyUSB0` 是动态串口节点，编号不代表固定物理插口。USB 拓扑路径与外壳插口标签的对应关系需实际确认。
- VID/PID 通常代表产品类型，不能独立区分多个同型号设备；序列号可能缺失或重复。
- 同一位置先后接入的设备不自动认定为同一实物，同一设备换口也不承诺身份连续。
- 同一 USB 父设备的多个功能归在同一连接下，分别维护通道信息；某通道消失与整台 USB 设备消失分别表达。
- 发现 CH340 不能确认它的 UART 引脚已经接板，也不能自动得知板型或波特率。
- 系统观察到消失、重现可能来自拔线、重启或模式切换，不推断未经证实的物理原因。
- 启动记录使用“启动时发现”和观察时间，不追溯实际插入时间。

## 4. 四个逻辑模块

| 模块 | 职责 | 输入与输出 |
|---|---|---|
| 规则管理与匹配 | 保存关注规则，按 VID/PID 匹配 | 修改请求 → 成功或失败；VID/PID → Key 或未匹配 |
| 系统设备采集 | 查询系统、扫描设备、监听变化 | 扫描调用 → 信息列表；系统事件 → 回调通知 |
| 历史记录 | 追加保存完整设备记录 | 完整记录 → 保存成功或失败 |
| 编排层 | 协调调用、组织记录、处理结果 | 接收业务请求和事件，保存后输出 |

```text
外部调用 / 程序启动 / 设备事件
                  │
                  ▼
                编排层
          ┌───────┼───────┐
          ▼       ▼       ▼
       规则模块  采集模块  历史模块
```

三个基础模块相互独立，由编排层协调。采集模块通过回调通知编排层；规则模块不主动扫描，历史模块不自行查询设备或匹配规则。

拆分用于明确职责、隔离文件和系统接口细节，不据此宣称性能提升。模块可先是同一程序中的类或文件，通过普通接口调用；独立进程、HTTP 服务、线程模型和具体目录均未确定。

## 5. 规则管理与匹配模块

### 5.1 规则与接口

- Key 是配置的类型标签，例如 `CH340`，匹配成功时返回。
- Value 是完整 VID/PID 二元组：输入设备 Value，查找对应 Key。
- Key 唯一，完整二元组也唯一，保持一一映射。同一个 VID 或 PID 单独重复不违反此约束。
- Key 不要求等于 Linux 驱动名，例如标签 `CH340` 与驱动 `ch341`。
- 提供读取、添加、修改、删除和匹配接口。
- 修改返回成功或失败；匹配区分匹配成功、未匹配、读取或解析失败。

规则使用 JSON 文件，例如：

```json
{
  "CH340": {
    "vid": "1a86",
    "pid": "7523"
  }
}
```

这里只示范一组编号，不代表全部 CH340。VID/PID 统一为规范化字符串后检查重复。

### 5.2 文件与并发

- 文件是规则的唯一依据，不维护长期内存规则缓存。
- 每次匹配读取文件，临时解析的数据只用于本次处理。
- 所有修改统一经过模块接口，当前不支持外部编辑器直接修改后自动检测。
- 读取使用共享锁，读完整内容后释放，再使用本次快照。
- 添加、修改、删除使用独占锁，覆盖完整的“读—校验—修改—保存”，避免并发修改覆盖。
- 保存成功、释放写锁后，编排层再调用扫描，不持有规则写锁执行设备扫描。

具体锁实现留到编码。如果使用临时文件原子替换 JSON，宜用独立稳定的锁文件，避免替换后仍锁着旧文件对象。原子替换避免读到半份文件；断电持久性及同步策略另行确定。

## 6. 系统设备采集模块

该模块使用已有 Linux 驱动，提供用户态设备采集能力。

### 6.1 全量扫描接口

- 获取当前相关 USB 设备及其资源信息。
- 从系统元数据读取位置、VID/PID、驱动及入口，按父子关系关联。
- 返回设备信息列表，由编排层执行关注规则匹配。
- 区分成功但无设备、扫描失败。
- 只读取元数据，不打开通信通道或重新初始化设备。

### 6.2 监听与停止

- 提供启动监听能力，通过异步通知或回调向编排层报告事件。
- 通知包含动作、观察时间和当时可获得的设备信息。
- 提供停止监听或取消订阅能力；具体为停止接口或可取消句柄，待实现时选择。
- 与扫描共用设备信息描述，允许事件中部分字段缺失。
- 不读取规则，不写业务历史，不决定最终对外输出。

启动时先建立监听再枚举，减少两者之间的遗漏窗口；期间允许重复观察。回调执行环境、扫描与事件的调度顺序留待实现时确定。

## 7. 历史记录模块

- 接收编排层组织好的完整设备记录。
- 规则文件与历史文件分开保存。
- 在文件末尾追加记录，不每次重写全部历史。
- 历史长期保留、人工清理，不自动过期删除。
- 返回保存成功，或保存失败及原因。
- 编排层仅在保存成功后向外提供正常设备结果。

文件操作、序列化、锁等优先使用现成能力。结构化历史格式尚未最终确定，JSON Lines 等为可选方案；追加并发控制、刷盘与异常恢复边界继续在具体实现中明确。

当前只围绕设备连接历史定义最小接口。后续有烧录等实际复用需求时再抽取通用部分；查询、索引、界面和通用事件协议暂不实现。

## 8. 编排层与数据流

编排层负责业务调用顺序、记录组织及失败处理。其具体类和执行模型暂不展开。

### 8.1 启动与主动扫描

```text
启动时建立监听 / 收到主动扫描请求
    ↓
采集模块扫描当前设备
    ↓
将设备 VID/PID 交给规则模块匹配
    ↓
结合 Key、位置、资源、时间和来源组织记录
    ↓
历史模块追加保存
    ↓ 保存成功
向外提供结果
```

每次全量扫描都可以为匹配设备产生新的“扫描发现”记录，允许重复，不要求扫描前后差分或重复事件消除。成功扫描可更新当前设备列表，记录必须区分扫描来源与系统事件，不能将重新扫描解释成实际重新插线。

### 8.2 运行期间的变化

```text
系统事件 → 采集模块回调 → 编排层
    ↓
结合可用元数据和必要的先前连接信息
    ↓
匹配、组织记录 → 保存成功 → 提供结果
```

保留移除通知，不能仅靠移除后的全量扫描恢复已消失设备的信息。关联移除所需的最小连接信息与长期缓存规则属于不同职责，具体状态结构待实现时确定。

### 8.3 修改规则

```text
编排入口接收规则修改
    ↓
规则模块加锁、读取、校验、保存、释放锁
    ↓ 保存成功
编排层立即调用全量扫描
    ↓
按更新后的规则匹配、记录当前设备
    ↓
返回规则修改与重新检查结果
```

采用同步调用顺序。保存失败时不发起这次扫描；保存成功但扫描失败时分别报告，不将已保存的规则描述为未修改。并发规则更新与事件到达时的调度策略仍需具体设计。
